# Responses 真实流式与前缀缓存验证

2026-10-29，物理 GPU 3，单张 A100 PCIe 40GB，TP1，W4A16 VOCAB4 权重、FP8 E4M3 KV、FLASHINFER、FULL_DECODE_ONLY、batch 512、MTP 关闭。所有实验由 24 GiB NVML 预算监督器管理；GPU 2 的常驻服务在实验期间独立运行。

## TPS 异常原因与修复

旧服务在提供 `tools` 时缓冲完整正文和参数，即使模型没有调用工具也如此。DSH 以第一个文本／推理／参数增量到结束事件之间的时间计算 TPS，因而会把几秒生成压缩成不足 1 ms 的发送窗口。诊断请求曾出现 87 个输出 token、1 个增量、约 0.817 ms 计时窗口，显示超过 10 万 token/s。无工具的对照请求有 92 个增量，显示约 64 token/s。

修复复用当前 NVIDIA vLLM 0.32 的 Qwen 增量解析器，Responses 和 Chat Completions 随生成发送内容。完整工具标记、调用策略及 JSON schema 通过校验后才发送完成事件。截断调用标记为 incomplete；失败不会损坏后续请求或引擎状态。Ascend 推理与原有解析路径保留。

输出用量仍取最终累计 token IDs 的长度，推理 token 是输出的子集。冷、热两组实验各返回 **3240 个输出 token**，分别与 vLLM 计数增加值 **3240** 完全相等。169 项回归通过，3 项缺少本地 Ascend tokenizer 的检查跳过；新增 ASGI 阻塞测试确认客户端在生成完成前收到增量。

## 测量结果

短输入固定生成 256 token；长输入精确为 16384 token，输出 128 token。工具调用样本实际生成 168 token，分为 **146 次参数增量**发送。客户端列使用与本地 DSH 源码相同的 `output_tokens / (结束时间－首增量时间)` 口径；引擎列使用 vLLM token 间隔计数与耗时。短工具调用还包含首个可见参数前的控制 token，因此两种口径不要求完全相等。

| 场景 | 并发 | 引擎解码 token/s/路 | DSH 口径 token/s/路 | 首字秒 | 合计端到端 token/s |
| --- | ---: | ---: | ---: | ---: | ---: |
| 无缓存，短输入，带 tools 普通回答 | 1 | 68.71 | 69.00 | 0.403 | 62.23 |
| 无缓存，短输入，带 tools 普通回答 | 2 | 66.27 | 66.50 | 0.666 | 112.97 |
| 开启缓存，短输入，带 tools 普通回答 | 1 | 69.05 | 69.28 | 0.465 | 61.54 |
| 开启缓存，短输入，带 tools 普通回答 | 2 | 66.21 | 66.46 | 0.692 | 112.30 |
| 16K 输入，首次请求 | 1 | 66.21 | 67.54 | 6.465 | 15.31 |
| 16K 输入，重复前缀，两次热测 | 1 | 66.29 | 67.49–67.54 | 0.450–0.491 | 53.58–54.54 |
| 16K 输入，首次请求 | 2 | 30.36 | 42.57 | 10.305 | 17.42 |

| 真实函数调用，开启缓存 | 1 | 68.64 | 73.87 | 0.657 | 57.31 |

两路时客户端列和首字列为两请求中位数，引擎列按 token 间隔加权。长输入的冷请求存在预填充与解码交错，因此解码期间也会受另一请求的输入计算影响。以上是指定输入的短测，不作为所有上下文长度的速度承诺。

## 缓存语义与正确性

- 关闭前缀缓存时，重复请求始终命中 0 token；开启后，16K 输入命中 **15680 token（95.70%）**，符合实际缓存块大小 1568。
- 同一 `prompt_cache_key` 改变输入开头后，命中回到 0。追加对话历史后，即使更换 key，也命中 15680 token 并按新问题返回 `OK`。key 只接收和回显；实际复用依据 token 前缀，不缓存最终回答，也不保存会话历史。
- 单路和两路的三次相同输入输出完全一致。16K 检索覆盖目标位于开头、中间、末尾，冷／热两轮、单／双路，共 **18/18** 回答正确，均无抢占。
- 官方 OpenAI SDK 严格校验通过 32K 输出上限、嵌套 questions 工具参数、工具回传、两路独立函数调用、追加历史及真实流式事件。无须修改 DSH 计时公式；旧会话中已经记录的错误速度不会自动重算。

## 两路完整 128K 容量实测

3 号卡独立压力实例开启前缀缓存，强制每路完整生成 32768 token。两个请求分别使用不同的唯一前缀，实际均为 **98304 输入＋32768 输出**，缓存命中均为 0；因此容量结论不依赖两请求共享前缀。

- 两路均成功完成，总输出 65536 token，总耗时 **800.057 秒**，含长输入处理的合计端到端吞吐 **81.914 token/s**。
- 全程零抢占、实例不变、设备独占；实际缓存池给出的满上下文驻留容量为 **2.02222**，配置仍限制两路。
- 100 ms NVML 采样记录的整卡显存峰值 **23.7514 GiB**，低于 24 GiB 监督阈值。此阈值是采样监督，并非硬件显存分区。
- 压力实例使用 `force_length=true` 验证容量；常驻服务关闭强制长度，模型正常停止。本项证明驻留与完成能力，不替代 128K 内容质量评测。

原始记录为 `capacity/capacity.json`、`capacity/context-131072-c2/98304-c2-none-r0.json`；停止后 GPU 3 的所属进程和显存已释放。

2 号卡常驻实例已按相同参数部署，关闭强制长度，监听 `0.0.0.0:8132`。通过服务器 IP 的官方 SDK 检查得到 80 次正文增量、4 次函数参数增量，重复约 4K 输入实际命中 3136 token；Chat Completions 流式也通过。部署检查的显存峰值为 23.6401 GiB，记录位于 `outputs/services/gpu2-24g-c2-prefix-20261029/deployment-smoke.json`。

## 实验记录与复现

原始数据位于 `outputs/responses-cache-20261029/`：`cold-clean/report.json`、`prefix/report.json` 保存逐事件时刻、响应、指标差值和设备盘点；`retrieval/` 保存检索答案；`sdk-smoke.json` 保存 SDK 验证。最初 `cold/` 的第二轮混入了独立 SDK 请求，被 token 对账拒绝，已标记整组无效，不参与以上结论。

冷对照 KV 预算 8.5 GiB；开启缓存时 GDN 状态从每组一个驻留块增加到两个，为保持两路 128K，KV 预算调整为 8.75 GiB。其余模型和推理参数一致。测试卡只运行一个实例，先停止并确认释放旧实例，再启动下一组。

```bash
export QWEN_NVIDIA_ENV=runtime QWEN_INSTANCE=vocab4-service-c2-20261029
source scripts/env_nvidia.sh
poetry run python -m tests.performance.nvidia.responses_probe \
  --url http://127.0.0.1:8133 --output outputs/新的独立测试目录
```

运行性能探针期间不要向同一实例发送其他生成请求，避免污染计时与 token 对账。部署状态和使用方式见 [GPU 2 服务说明](nvidia-gpu2-service.md)。
