# 主程序 W4 快速解码接入与重复对照

快速解码已经接入 `src/qwen_llm` 的正式执行路径。原实验入口复用同一实现，不再维护独立的分派类。只在 Qwen3.8 BF16 专项适配中，对 M=6/12 的 128 个目标 FFN 投影选择 `inner_precise=1`；其他形状使用原调用。原始 NZ 权重、BF16 尺度、MTP2、输出头共享和 KV 配置保持。

## 正式入口

```bash
source scripts/env_ascend_291.sh
poetry run qwen-llm serve-model qwen3.8-27b-optimized-v1 --qwen38-fast-w4
# 回退到默认计算分支
poetry run qwen-llm serve-model qwen3.8-27b-optimized-v1 --no-qwen38-fast-w4
```

直接调用 `serve` 也支持这两个选项。环境变量为 `QWEN38_FAST_W4`；模型目录可使用布尔字段 `qwen38_fast_w4`，显式 CLI 参数优先。通用配置默认关闭，不能对其他模型适配启用。

`/health/ready` 中实际 Worker 的 `model_adaptation.w4_decode` 报告后端、覆盖层数、快速 M、回退模式和额外权重字节数。验证目标是正式 `qwen_llm.engine.qwen38_worker.Qwen38NPUWorker`，没有诊断 Worker 或 profiler 注入。

分派通过 `torch.library.custom_op` 注册的不透明节点 `qwen_llm::fast_w4` 完成，防止动态编译在大 M 的预运行中固定 Python 条件分支。实际计算仍调用原生 W4 算子，没有新增 AscendC 算术内核。Fake 实现只推导形状；真实张量按具体 M 选择模式，再捕获到 NPU 图中。`capture_dispatch` 记录 eager/图捕获期间的实际模式，图重放不会增加该计数。

首个优化进程的生成图确认有 128 个 `qwen_llm.fast_w4.default` 节点，运行记录中 `6:1`、`12:1` 各 256 次，`3:0` 为 256 次。验收要求两个优化进程都记录至少 128 次 `6:1` 和 `12:1`。

## 稳定性检验设计

有效对照目录：`/home/qwen-models/reports/qwen3.8-27b/main-fast-w4-opaque-20261103`。

使用 B/A/A/B 四次独立进程启动：优化 B1、原生 A1、原生 A2、优化 B2，以先检查实际加速分派，同时平衡启动顺序。每次仅测两并发和四并发的 512 输出 token，预热一次后测三轮。每个模式每个场景共六轮，跨两次独立启动；不运行完整质量集或长输入测试。

先前 `main-fast-w4-stability-20261103` 中仍使用 Python 条件分支，已标记为被替代。旧 V3 服务短测也存在同样问题，其 +4.7%/+3.0% 不能归因于加速，已同步更正旧报告。两份实验的编译图诊断和原始数据均保留，独立算子数值/计时结果仍有效。

两种模式使用相同模型、输入、随机种子、生产入口、设备、CPU 调度范围和配置，唯一实验变量是快速解码开关。四份生产源码与模型目录配置快照必须一致。退出后核对设备与端口释放，每次测试中只允许一个 NPU Worker。

驱动主动发送 SIGTERM 结束服务；Uvicorn 部分启动会在完整执行 lifespan 清理后重新抛出该信号，因此保留原始退出码，并仅接受 0，或带有 `Application shutdown complete.` 日志的 -15。请求检查与设备/端口释放仍须全部通过，强制 SIGKILL 不接受。

事先锁定的稳定收益标准：两个场景均须满足“较慢的优化进程中位数 / 较快的原生进程中位数 ≥ 1.01”，六轮吞吐变异系数不超过 5%；请求、实际模式、四路完整上下文容量、MTP2、图捕获与资源释放全部通过。额外就绪时分配 HBM 不超过 1 GiB。普通回答、结构化 JSON 和取消回收检查在吞吐测量之后运行。

这检验的是跨启动的短吞吐稳定性，不代表小时级稳态或完整质量验收。若重复收益不满足标准，保留主程序开关并保持默认关闭。

汇总入口：`poetry run python -m tests.performance.qwen38.summarize_main_fast_w4 实验目录`。各任务保留精确命令、源码、逐轮 HTTP/SSE、就绪状态、NPU 盘点和退出状态。
